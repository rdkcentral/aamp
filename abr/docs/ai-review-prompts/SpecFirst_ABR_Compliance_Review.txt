REVIEW RULES (STRICT)
- Only claim behavior you can point to in the provided code/text/logs.
- If the code is missing information, say “Not determinable from provided inputs.”
- Treat MUST / MUST NOT as hard requirements; SHOULD as guidance.
- Do not redesign the system; focus on compliance and minimal fixes.

TASKS
A) Build a Spec → Code Traceability Matrix
For each numbered spec section and rule:
- Status: {PASS | FAIL | PARTIAL | NOT FOUND | NOT DETERMINABLE}
- Evidence: quote exact code lines/snippets (or pseudo-line references like file:function:statement)
- Explanation: why it passes/fails based on the spec
- Risk: user impact if violated (freeze risk, latency drift, thrash, etc.)

B) Identify Semantic Mismatches & Ambiguities
- List any spec terms not implemented as defined (e.g., buffer semantics, predicted underflow definition, stableBufferTime reset)
- List any code behavior that contradicts the spec (e.g., targetLatency goes below default, repeated danger-episode bumps, ABR factoring playbackSpeed)

C) Recommend Minimal Corrective Changes
For each FAIL/PARTIAL:
- Suggest the smallest change that brings code into compliance
- Include the exact decision rule or invariant being fixed
- Avoid refactors unless required for compliance

D) Propose Targeted Test Cases
Give a small set of deterministic tests that prove compliance:
- Unit tests (logic-only) for: predicted underflow, profile choice, “all profiles unsafe” fallback, stableBufferTime reset behavior, danger episode one-shot, clamping.
- Integration tests (simulated network) for: bail triggered mid-download, recovery behavior, latency speed transitions w/ variance and “must pass through 1x”.

OUTPUT FORMAT (REQUIRED)
1) Executive Summary (5-10 bullets)
2) Traceability Matrix (grouped by spec sections)
3) Findings (FAIL/PARTIAL/NOT FOUND)
4) Minimal Fix Suggestions (actionable)
5) Test Plan (bullet list with scenario + expected outcome)
6) Open Questions (only if truly not determinable from inputs)
