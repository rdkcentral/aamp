# DATA register fragment

Workaround and improvement rows for the Media data path page (03). Recovered and re-verified after the original data-path agent stalled before writing this file.

| ID | Location | Type | What and why | Risk/impact | Suggested improvement | Effort |
|---|---|---|---|---|---|---|
| DATA-01 | `AampRialtoNeedDataHandshake.cpp:WaitForAttach`, `WaitForGate`, `WaitForRequest` | Limitation | Every injector wait is an untimed `cv.wait`. A wait ends only on its condition or a generation bump (Flush/Stop/Configure/new session). | If Rialto stops sending needData (server stall, lost IPC event), injector threads block forever and AAMP's track join in `StopInjectLoop` depends entirely on `UnblockTrackInjection`. Hangs are silent: there is no log while blocked. | Add a long diagnostic timeout (log and keep waiting) to make stalls visible. Consider an optional abort timeout with a playback error. | S |
| DATA-02 | `AampRialtoPlayer.cpp:OnNeedMediaData` | Tech-debt | Logs `sourceId/frameCount/requestId` at INFO on every needData, although `AampRialtoMediaSource::handleNeedData` already rate-limits its own INFO log to the first and every 100th request. | Log flooding on the Rialto event thread at tens of requests per second per track. This costs CPU and hides useful INFO logs on embedded targets. | Drop to TRACE, or reuse the `kNeedDataLogInterval` cadence. | S |
| DATA-03 | `AampRialtoPlayer.cpp:DeferAttachUntilVideo` | Workaround | Same item as ARCH-13. Non-video sources wait for the video attach, because a first tune that attached audio first gave `audsrc: not-linked (-1)` and an ERROR. The root cause was not established (a first-pipeline-after-boot race is suggested in the comment). | Adds startup latency and an untimed wait (DATA-01). The real defect may be in Rialto or the server and could resurface in other orderings. | Reproduce against the Rialto server and either fix the root cause or document the required attach order as a Rialto contract. | M |
| DATA-04 | `AampRialtoVideoSource.cpp:createRialtoSource`, `AampRialtoAudioSource.cpp:createRialtoSource` | Workaround | `hasDrm` is hard-coded `true` for video and audio sources, and the incoming argument is ignored. The code comment says this avoided a Rialto Server crash seen during testing. The GStreamer path passes `false` for clear HLS-TS. | Clear content always goes through the DRM-capable decode path, so the decoder/pipeline choice may differ from the GStreamer path. The server crash is hidden rather than fixed. | Raise with the Rialto owners. Once fixed, pass the real `hasDrm` value and add an L1 test that it is propagated. | M |
| DATA-05 | `AampRialtoAudioSource.cpp:mapCodecToMime` | Workaround | AC-3 and EAC-3 both map to `audio/x-eac3`, to match the mapping in the pinned rialto-gstreamer v0.20.1. | Pure AC-3 relies on the server's EAC-3 decoder accepting AC-3. If a future Rialto version separates the mimes, AC-3 could fail or be misidentified. | Revisit when the Rialto version is bumped. Add a version note or `audio/x-ac3` once supported. | S |
| DATA-06 | `AampRialtoPlayer.cpp:SendCopy` (muxed HLS-TS attach) | Workaround | All sources are attached on the first TS frame, with a `MediaCodecInfo` holding only the codec format, to avoid a deadlock: the single TS injection thread would otherwise block in `injectOneSample` before attaching the other tracks. | Width, height, channels, sample rate and codec data are zero/empty on this path, so Rialto must infer them from the elementary stream. Any change to attach ordering can reintroduce the deadlock. | Document the invariant in code near `SendCopy`. Add an L1 test for "muxed TS attaches all sources before the first inject". Optionally pass the full caps once the PMT and first frames are parsed. | M |
| DATA-07 | `AampRialtoPlayer.cpp:SendCopy` -> `injectOneSample(morePending=false)` | Tech-debt | Each HLS-TS ES frame is injected with `morePending=false`, so every frame closes its batch with `haveData(OK)`, which is one IPC round trip per frame. | Extra IPC traffic and needData churn for HLS-TS compared with fMP4 batching. Higher CPU on low-end devices. | Pass `morePending=true` within a TS chunk and close the batch at the chunk end. This needs care with buffer lifetime (DATA-17). | M |
| DATA-08 | `AampRialtoMediaSource.h:processDataFragment` (via `SendTransfer`) | Possible bug | `fragmentPTSoffset` is accepted by `SendTransfer` but the parameter is unnamed and unused, so internal `Mp4Demux` timestamps are used raw. | If this path carries media with PTS restamping enabled, those samples are off by the restamp offset compared with samples from `AampMp4Demuxer`. See DATA-09 for reachability. | Apply the offset as `AampMp4Demuxer` does, or assert that the path is only used when the offset is 0. | S |
| DATA-09 | `AampRialtoMediaSource.cpp:processInitFragment`/`processDataFragment` and `mp4demux/AampMp4Demuxer` | Tech-debt | There are two MP4 demux paths. `AampMp4Demuxer` (normal, `useMp4Demux` forced on) and an internal `Mp4Demux` inside the source for `SendTransfer`. The internal one appears reachable only for tracks without a `playContext`. | Duplicated logic, and divergent behaviour (DATA-08). Maintainers fix one path and not the other. | Confirm reachability with logging or L2. Remove the internal demux path or route it through `AampMp4Demuxer`. | M |
| DATA-10 | `mp4demux/AampMp4Demuxer.cpp:abort` (`mAborted`) | Workaround | Part of ARCH-28. This sits outside direct-rialto. `AampMp4Demuxer` has an abort flag checked between samples, because the sink's `SendSample` result is not propagated back. Without it, a demuxer loop keeps feeding a fragment's remaining samples into a flushed or stopped player. | Extra cross-component coupling. Behaviour depends on the flag being set before the flush/stop generation bump. | Have `SendSample` return a "stop feeding" result that the demuxer honours, and remove the side-channel flag. | M |
| DATA-11 | `priv_aamp.cpp:PrivateInstanceAAMP::StopTrackInjection` -> `StreamSink::UnblockTrackInjection` | Workaround | Part of ARCH-28. This sits outside direct-rialto. Because direct-rialto blocks injector threads while waiting for needData, `StopTrackInjection(discard)` must call `UnblockTrackInjection(type)` before `StopInjectLoop` joins the thread. It must run even if the track is already marked blocked, otherwise the join hangs forever (code comment). | Core AAMP now carries sink-specific unblock logic. Any new path that joins injector threads without calling it can deadlock. | Make "unblock before join" part of the `StreamSink` contract (document it on the interface) and cover it with an L1 test of `StopTrackInjection`. | S |
| DATA-12 | `AampRialtoPlayer.cpp` subtitle caps update -> `ResumeTrackDownloads(eMEDIATYPE_SUBTITLE)` | Workaround | `ResumeTrackDownloads` is never triggered by a Rialto needData, so the player explicitly resumes subtitle downloads after a subtitle caps update. Otherwise subtitle fetching stays stopped. | Download flow control for direct-rialto differs from GStreamer (DATA-18). It is easy to miss for new track types. | Centralise download resume/stop decisions (see DATA-18). | S |
| DATA-13 | `AampRialtoPlayer.cpp:OnNeedMediaData` (unknown `sourceId`) | Possible bug | A needData for a Rialto source id with no matching source is logged at WARN and never answered. | If it ever happens (for example a late request for a source removed during reconfigure), Rialto may keep waiting for that request and stall that source until cancel or flush. Impact depends on the server's request timeout, which is unknown (page 03 Open questions). | Reply `haveData(NO_AVAILABLE_SAMPLES)` to unknown sources when the pipeline exists. | S |
| DATA-14 | `AampRialtoPlayer.cpp:OnSourceNewlyAttached` (audio-only, commit `673f66d1`) | Limitation | `PositionPending` is released only on a video attach, so audio-only tunes always resolve their start position through a deferred flush on the first sample. | An extra Flush/SEEK_DONE cycle on every audio-only tune adds startup latency. It may be unintended. | Release `PositionPending` for the primary source (audio when there is no video). | S |
| DATA-15 | `AampRialtoPlayer.cpp:SendCopy`, `SendTransfer` ("No source" branches) | Stale comment | Same item as ARCH-05. The comment "No source for this track (e.g. subtitle not yet supported)" is out of date: subtitle sources are supported (`AampRialtoSubtitleSource`). The common real cause is DSM-CC/ID3 packets, or tracks not configured. | Misleads readers when diagnosing "No source" logs. | Update the comment to list the real causes (ID3/DSM-CC, disabled track). | S |
| DATA-16 | `AampRialtoNeedDataHandshake.cpp:WaitForAttach` vs `AampRialtoPlayer.cpp:ReportAttachFailure` | Possible bug | `ReportAttachFailure` clears `attachPending` and calls `notify_all`, with a comment saying waiters "now discard their frame". The `WaitForAttach` predicate is only `attached() \|\| generation changed`, so a waiter woken this way re-checks, finds neither true and goes back to sleep. | After a failed deferred attach (for example video codec unmapped), the audio injector stays blocked until the next Flush/Stop/Configure, and the AAMP track thread appears hung. | Add `!m_state.attachPending` to the predicate and return `Aborted` in that case. Add an L1 test. | S |
| DATA-17 | `AampRialtoMediaSource.cpp:injectOneSample` (segment buffer lifetime) | Limitation | Segments reference the caller's buffer without copying. Rialto documents that the buffer must stay valid until the matching `haveData()` completes. Validity is only ensured implicitly by forcing `haveData` at `morePending == false`. The NO_SPACE path replies while a retained sample is still pending. | A latent use-after-free risk if batching rules change (for example DATA-07) or a caller frees the buffer early. | State the invariant in code and on page 03, and confirm with the Rialto owners whether `addSegment` copies into shared memory synchronously. | S |
| DATA-18 | `AampRialtoPlayer.cpp` (no `BlockUntilGstreamerWantsData` equivalent) | Limitation | Back-pressure is applied only by blocking the injector inside `Send*`. needData and buffer-full are not translated into AAMP `StopTrackDownloads`/`ResumeTrackDownloads`, unlike the GStreamer sink. | AAMP's fragment cache fills and download throttling is indirect, so ABR and buffer-health metrics may behave differently from the GStreamer path. Leads to special cases like DATA-12. | Decide whether direct-rialto should signal download flow control explicitly, and document the chosen model. | M |
| DATA-19 | `AampRialtoMediaSource.cpp` (`addSegment` ERROR, `haveData` failure) | Limitation | An `addSegment` ERROR counts the sample into the batch and does not retry. A failed `haveData` is logged at WARN with no retry or error escalation. | A transient IPC failure silently drops media (a picture or audio glitch) or leaves a request unanswered. | Count and surface repeated failures (for example escalate to a playback error after N consecutive failures). | S |
| DATA-20 | `AampRialtoMediaPipelineClient.cpp:notifySourceFlushed`, `notifyPlaybackInfo`, `notifyFirstFrameReceived` | Stub | Same item as ARCH-14. These Rialto client callbacks are no-ops ("Not Implemented"). `notifySourceFlushed` is intentionally unused because Flush uses pipeline-level `setPosition` and SEEK_DONE. | `notifyFirstFrameReceived` could drive a precise first-frame or tune-time metric. `notifyPlaybackInfo` could provide position/QoS without polling. Both are currently unused. | Evaluate wiring `notifyFirstFrameReceived` to AAMP's first-frame notification, and `notifyPlaybackInfo` to position reporting (see page 08). | M |
