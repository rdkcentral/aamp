| THR-01 | `AampRialtoPlayer.h:AampRialtoPlayer` (class threading comment, lock-order comment beside `m_attachMutex`) | Stale comment | The comment is mostly accurate but omits three things: `Configure()` can also run on the TS injector path (`SetStreamFormat`); progress ticks can run on the thread calling `FireNowIfRunning` (usually the Rialto event thread); and two nestings under `m_attachMutex` (state-machine mutex, play lock leading to `play()`/`pause()` IPC). | Contributors rely on the comment to reason about deadlocks, and the omissions are exactly the non-obvious paths. | Update the comment to match page 05 section 4. | S |
| THR-02 | `AampRialtoPlayer.cpp:Configure` / `BeginNewSession` | Possible bug | `Configure()` does not take `m_flushCallMutex`. The comment beside that mutex assumes AAMP stops injection before calling `Configure()`, but for muxed HLS-TS `TSProcessor::processPMTSection` calls `SetStreamFormat` and then `Configure()` on the injector path. | Source reset and session reuse can interleave with a control-thread `Flush()` or with an elected injector's deferred flush. The effect is unproven but there is no serialisation. | Take `m_flushCallMutex` in `Configure()`, or document and assert the AAMP-side guarantee that makes it unnecessary. | M |
| THR-03 | `AampRialtoPlayer.cpp:HandlePlaybackStarted` -> `StartProgressTimer` -> `AampRialtoProgressTimer::start` | Possible bug | Commit `7efb0a89` made `kick()` unable to restart a stopped timer, but when the timer is not running `StartProgressTimer()` calls `start()`, which does create a new timer. `HandlePlaybackStarted` does not check the state machine, so a PLAYING event processed after `Stop()` restarts progress reporting (and `m_monitorAV->start()` if a monitor exists). | Progress events and ticks on a stopped player until the next `Stop()` or destruction. | Ignore PLAYING when the state machine is IDLE or ERROR, or have `Stop()` latch a "stopped" flag checked by `StartProgressTimer`. Add an L1 test. | S |
| THR-04 | `AampRialtoPlayer.cpp:ApplySubtitleSegmentPosition` (event thread) vs `AttachSource` (injector, `m_attachMutex` across `AampDrmBridge::createSession`) | Limitation | The `SEEK_DONE` handler takes `m_attachMutex`. If an injector holds it during a blocking licence fetch, the Rialto event thread waits, and every Rialto event (needData, state, position) waits with it. Same root cause as ARCH-04 (mute calls). | Seek completion can be delayed by seconds and the flush may hit its 5000 ms timeout, giving visible stalls on encrypted content with subtitles. | Do not hold `m_attachMutex` across `createSession`: fetch the licence first, then attach under the lock. Alternatively use a dedicated subtitle-position lock. | M |
| THR-05 | `AampRialtoPreRollMonitor.cpp:Poll` -> completion -> `AampRialtoPlaybackController::ReleaseHold` -> `AampRialtoPlayer::IssuePlay` | Tech-debt | When pre-roll completes, `play()` (a synchronous Rialto IPC) and the source ungate run on the GLib main loop thread, which belongs to the host application. | The host's UI or event loop is blocked for the IPC call. If the host loop also serves Rialto IPC, there is a risk of priority inversion. | Post the completion to the AAMP scheduler (or another worker) instead of running it in the tick. | M |
| THR-06 | `AampRialtoPlaybackController.cpp:Dispatch` (`playLock.unlock()` before the pre-roll action) | Possible bug | The play lock is a recursive mutex. `Dispatch` releases one level before starting pre-roll, because `AampRialtoPreRollMonitor::Start` may wait for a `Poll` that needs the play lock. If the caller already held the play lock (nested `ReleaseHold`), one level stays held. | Deadlock between the caller and the GLib thread if such a nested path is ever taken. No current path was found. | Assert the recursion depth is 1 (count nesting in the controller), or restructure so pre-roll start never runs under the play lock. | S |
| THR-07 | `AampRialtoSegmentPosition` (`m_stagedPositionNs`, `m_stagedRate`) | Limitation | Position and rate are separate atomics. The header contract says they are a consistent pair only while FLUSHING. Readers outside FLUSHING can see a new position with the old rate. | Brief wrong rate in position or trick-play calculations around a flush boundary. Low impact today. | Pack position and rate into one struct behind a small mutex or a sequence lock if more readers appear. | S |
| THR-08 | `test/utests/tests/AampRialto*` | Tech-debt | No L1 test drives two threads into the player at once. Every hazard on page 05 section 8 is unverified by tests, and the lock order is enforced only by review. | Regressions in teardown and flush races are found only on devices. | Add a small set of deterministic interleaving tests using the fakes (for example Stop vs late PLAYING, Stop vs blocked injector), and consider a debug-build lock-order checker. | M |
| THR-09 | `AampRialtoPlayer.cpp:GetVideoPlaybackQuality` (`m_playbackQuality`) | Possible bug | Writes the unguarded member `m_playbackQuality` and returns a pointer to it. It is safe only while exactly one thread calls it. | A data race and a torn result if a second caller is ever added. | Return the struct by value, or guard it and copy it out. | S |
