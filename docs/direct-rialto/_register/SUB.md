| SUB-01 | `AampRialtoSubtitleSource.cpp:processInitFragment` (only caller of `m_ttmlOffset.Reset()`) | Possible bug | The TTML mode (`PASSTHROUGH` / `LINEAR_OFFSET`) is reset only in `processInitFragment`. The MP4 subtitle path (`AampMp4Demuxer` -> `SetStreamCaps`) never calls it, and raw TTML usually has no init fragment. The header comment says Configure() resets it, but `reset()` does not. A rebuilt pipeline gets a new source; a **reused** pipeline keeps the old decision across seeks, period changes and ad transitions. Once `PASSTHROUGH` is chosen, every later document gets offset 0. | Content whose cue-time style changes between periods (for example an SSAI ad with relative times followed by live content with absolute times) shows subtitles at the wrong time, or not at all. | Reset the TTML state in `updateCachedMetadata` / on caps change and on flush, and fix the header comment. Add an L1 test for PASSTHROUGH followed by absolute times. | S |
| SUB-02 | `AampRialtoSubtitleSource.h:isInbandCC` comment; `AampRialtoPlayer.cpp:CreateSubtitleSource` comment | Stale comment | The `isInbandCC` doc says it is "set internally by mapCodecToMime() when the codec format resolves to GST_FORMAT_UNKNOWN"; it actually tests `format() == FORMAT_INVALID`. `CreateSubtitleSource` says the inband CC source uses `"application/x-subtitle-cc"`; the mime is `"text/cc"`. | Misleads anyone debugging CC attach or reading Rialto server logs. | Correct both comments. | S |
| SUB-03 | `AampRialtoPlayer.cpp:CreateSubtitleSource` (synthesised attach for `FORMAT_SUBTITLE_MP4`) | Possible bug | For subtitle-in-MP4 the player queues an attach with a synthesised `GST_FORMAT_SUBTITLE_TTML` codec, deferred only until video attaches. `AampMp4Demuxer` later calls `SetStreamCaps` with the real codec (`wvtt` reports `GST_FORMAT_SUBTITLE_WEBVTT`), but an already attached source is only updated for protection, so its mime cannot change. If the synthesised attach wins the race, WebVTT-in-MP4 is attached as `text/ttml` and its documents go through the TTML offset parser. | WebVTT-in-MP4 subtitles may not render, or be mistimed, depending on attach ordering. Unverified on devices. | Do not queue a synthesised attach for `FORMAT_SUBTITLE_MP4`; wait for `SetStreamCaps` (the source is still created so the source set is complete). | S |
| SUB-04 | `AampRialtoPlayer.cpp:SetSubtitlePtsOffset` | Stub | Logs ENTRY/EXIT and does nothing. The GStreamer path sends a `set-pts-offset` event to the subtitle sink; direct-rialto relies on the per-segment display offset instead. | Harmless today, but callers cannot tell it is ignored, and any AAMP feature relying on it (for example a late offset change) silently has no effect. | Document it as intentionally unused in the `StreamSink` override, or apply it as an additional display offset. | S |
| SUB-05 | `AampRialtoPlayer.cpp:SetSubtitleMute` vs `setCCMute` | Tech-debt | Both call `setMute` on the same subtitle source. `SetSubtitleMute` caches `m_subtitleMuted` (re-applied on attach); `setCCMute` does not update that cache. If the CC manager unmutes before the source attaches (returns false) and the source then attaches, the cached sidecar mute value (default true) is applied instead. | Low today: the CC manager is first initialised at the first `PLAYING`, after the source has attached. It becomes a bug if CC control ever happens earlier, or across a detach/re-attach on period transitions. | Share one cached mute state, or have `setCCMute` update `m_subtitleMuted`. | S |
